Yukkuri 乐园：技术选型建议 v001
日期：2026-10-25（Asia/Shanghai）
依据：requirements-v001.txt 至 requirements-v020.txt、design-overview-v001.txt、demo-plan-v001.txt。
状态：技术建议及验证候选，不是用户已确认的最终选型；未安装工具、未建工程、未完成性能或交互验证。

一、推荐候选
Godot 4 稳定版的 .NET 构建＋C#，锁定实测通过的引擎、对应导出模板及兼容 .NET SDK 版本。
采用真实 3D 场景、斜俯视正交镜头实现 2.5D，互动时靠近同一个体。
C# 同时用于游戏逻辑与引擎接入，初期不无必要地混合多套脚本语言。
Blender 制作或修改模型、UV、骨骼与形变，运行资产采用 glTF/GLB。
Git 管理源码、文本场景与配置，较大二进制资产按需使用 Git LFS；不提交临时导入缓存和构建结果。
Windows 本地游戏，Godot 原生 UI；台词、物品、性格等以数据表/JSON 配置，文本使用语言键。
存档采用带 schemaVersion 的数据快照，初期可用压缩 JSON、临时文件写入后替换与轮换备份。读取失败保留旧存档，不覆盖唯一可用副本。

二、为什么优先验证这一组合（项目判断，不是普遍优劣排名）
支持命令行导入、运行与导出，适合可重复的 AI 开发流程；仍需实际画面和操作检查。
C# 类型与独立逻辑项目有利于处理复杂状态和自动化验证；选择它不等于宣称 GDScript 无法承载 100 只个体。
Windows 单人目标符合该路线，当前不需要以网页导出作为主交付。
Godot 的 MIT 许可允许商业与闭源游戏，发布时保留规定的版权/许可告知；第三方资产和插件另行核查。
当前 PATH 未发现 Godot、Blender 和 dotnet，不代表全盘未安装；实际准备时先确认具体安装位置再获取工具。

三、软件结构建议
Simulation：尽可能不依赖 Godot 节点的 C# 模拟核心，包含个体需求、性格、关系、遗传、伤情、经济、地区和事件。
Presentation：Godot 场景、动画、音效、UI、镜头和玩家输入；向模拟核心提交动作，不各自持有冲突的真实性格副本。
Persistence：存档、版本迁移、备份、配置校验，统一保存跨地区状态与随机数生成器状态。
Platform：Steam 能力经独立适配层接入；本地 Demo 的游戏运行不依赖 Steam 登录。插件候选须单独验证 C#、引擎和 SDK 版本兼容性，不预先声称已接入。

四、关键实体和时钟
持续个体身份、身体、登记身份分别建模，用稳定 ID 关联。
记忆/关系/性格跟随持续个体；身体素质/物种跟随当前身体；评级与冒用身份另行记录。
真实性格和观察档案分开，允许低技能误判与后来纠正，不能把观察标签当作真实性格源。
世界模拟时钟与近景交互/视觉更新分开：特写冻结世界被动推进，目标仍响应动作，不因停留时间独自成长。
正常跨区按世界时钟简化模拟，关闭游戏不按现实时间补算。
重建渲染场景不能重新生成个体身份或性格；同一存档须恢复相同数据状态。

五、物理与形变建议
先验证 Godot 内置 Jolt 作为碰撞、刚体和拿取约束基础。
日常角色采用简化碰撞与受控移动；特写目标提高交互精度。
柔软视觉使用骨骼、形态键或局部形变响应接触点与力度；物理碰撞和可视网格变形需要协调，不能只做手感无关的动画。
不预先承诺对 100 只个体同时做高精度全软体，也不将用户物理互动需求缩成菜单选择。
Jolt/Godot 有关节参数差异，具体拿取约束必须实际验证，不把引擎名称当作功能验收。
真实 3D 场景不要求玩家能自由旋转整个地图；镜头能力仍服从已确认设计。

六、模拟性能策略
可见动画/渲染、物理与高层决策分别调度；高层需求/社交不需要每帧全体重算。
附近个体用空间索引查询，关系使用稀疏记录，重要记忆与事件按设计保留，避免默认每帧所有个体两两比较。
未访问地区保留真实数据和计时事件，简化呈现与行动细节；重要不可逆事件仍遵守用户选定的持续模拟规则。
从普通数据结构和明确模块开始，测量发现瓶颈后再优化；不先上复杂 ECS、原生扩展或分布式系统。
保存随机状态有助于重现模拟，但不能因此声称跨机器刚体物理完全确定性。
50/100 只性能、跨区与近景切换均需实际测量，尚未给出帧率承诺。

七、其他引擎比较
Unity 6＋C#：可行备选，尤其当关键资产或插件依赖 Unity 时值得重新比较；同样具备自动化能力，不能以“只能手点编辑器”为由排除。
Unity 当前已取消 Runtime Fee；Personal/Pro 等资格仍依收入与资金等条款区分。不用过时安装收费说法做选型依据。
Unreal：具备强大的 3D 能力，但基于本项目画面目标和单人 AI 开发条件，当前不优先承担其额外工程与内容工作流复杂性。这是项目判断，不是能力不足。
不建议先用浏览器技术做主游戏再迁移，当前首发目标是 Windows 原生、3D 物理与近景交互。

八、选型验证门槛
1. Windows 上建立 .NET 工程，执行构建并导出可运行程序，实际启动检查。
2. 一个角色完成拿起、放下、接触力度反馈和近景表情；检查接触穿透、抖动与形变。
3. 对 50 与 100 只进行移动、需求和事件模拟，记录机器、帧率/帧时间和问题。
4. 同一个体近景/远景、切区、存读档后保持身份和状态；错误观察不得改写真实性格。
5. 子弹时间中仅动作结算，世界及后台地区不偷偷推进；退出不重复扣除资源。
通过以上早期验证后固定主版本；如技术约束不满足需求，再依据实测比较替代方案，不在大规模内容制作后才暴露。
